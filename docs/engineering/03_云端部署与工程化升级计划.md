# MediGenius 云端部署与工程化升级计划

本文档整理 MediGenius 后续面向云端部署、稳定运行、安全登录和高频请求快速响应的工程化升级计划。

## 1. 升级目标

当前项目已经具备医学问答、LangGraph Agent 工作流、RAG 检索、聊天记录和 ECG 报告能力。后续升级重点不是单纯增加某个中间件，而是把系统从单机原型改造成可上线运行的服务：

- API 服务无状态化，支持多实例部署和水平扩容。
- Agent、RAG、ECG 报告等耗时任务可排队、可重试、可限流。
- 登录认证从明文 ID/password 模式升级为安全会话体系。
- 引入 Redis 支持语义缓存、任务状态、限流和并发去重。
- 数据和文件存储从本地依赖迁移到云端友好的持久化服务。
- 建立日志、监控、审计和告警，支持线上问题定位。

## 2. 阶段一：安全登录与基础后端改造

目标：先解决明文登录、单机存储和基础 API 安全问题。

### 2.1 用户系统

- 新增 `users` 表，保存用户基础信息。
- 密码必须使用 `Argon2id` 或 `bcrypt` 哈希存储。
- 禁止在数据库、日志、接口响应中出现明文密码。
- 用户 ID、会话 ID、报告 ID 使用不可预测 ID，避免递增 ID 被枚举。

### 2.2 登录接口

新增认证接口：

```text
POST /api/v1/auth/login
POST /api/v1/auth/refresh
POST /api/v1/auth/logout
GET  /api/v1/auth/me
```

推荐流程：

1. 用户通过 HTTPS 调用 `/auth/login`，提交 `username/password`。
2. 后端校验密码哈希。
3. 登录成功后返回短期 `access_token`。
4. `refresh_token` 用于续期，建议放入 `HttpOnly + Secure + SameSite` Cookie。
5. 后续业务接口使用 `Authorization: Bearer <access_token>`。

### 2.3 会话安全

- `access_token` 有效期建议为 15 到 30 分钟。
- `refresh_token` 支持轮换，旧 token 使用后立即失效。
- 支持登出失效。
- 支持多设备会话管理。
- 登录失败增加用户级和 IP 级限流。
- 异常登录、频繁失败登录写入审计日志。

### 2.4 数据存储升级

- SQLite 迁移到 PostgreSQL。
- 聊天记录、用户画像、任务状态、审计日志进入 PostgreSQL。
- 不再依赖本地 JSON 文件保存用户画像。
- 本地 PDF 报告迁移到对象存储，例如 S3、OSS、COS。

### 2.5 基础 API 安全

- CORS 使用明确白名单。
- 请求体大小限制。
- API 入参统一使用 Pydantic schema 校验。
- 日志脱敏，避免记录 password、token、手机号、身份证号、完整病历等敏感信息。
- 统一错误响应格式，避免向前端暴露内部异常堆栈。

## 3. 阶段二：Redis 与语义缓存

目标：降低重复请求成本，提高常见低风险问答的响应速度。

Redis 不只用于普通 key-value 缓存，还应承担以下职责：

- 语义缓存。
- 任务状态缓存。
- 用户/IP 限流计数。
- 并发去重锁。

### 3.1 语义缓存设计原则

用户每次 query 可能表达不同但语义相同，例如：

```text
高血压能不能喝咖啡？
血压高的人可以喝咖啡吗？
有高血压，咖啡还能喝吗？
```

因此不能使用完整 query 作为 Redis key，也不能只使用 `sha256(query)`。推荐使用语义缓存：

- query 生成 embedding。
- Redis Vector Search 查询历史语义相近问题。
- 通过相似度、意图、医学实体、风险等级等条件判断是否复用答案。
- key 中只保存 `semantic_id` 或语义指纹，不保存完整 query。

### 3.2 推荐 Key 设计

```text
mg:semcache:index:chat:v1
mg:semcache:answer:chat:v1:{semantic_id}
mg:semcache:lock:chat:v1:{semantic_fingerprint}

mg:job:{job_id}
mg:rate:user:{user_id}:minute:{yyyyMMddHHmm}
mg:rate:ip:{ip}:minute:{yyyyMMddHHmm}
mg:lock:job:{dedupe_hash}
```

说明：

- `mg` 是项目命名前缀。
- `v1` 是缓存结构版本，Prompt、模型或 RAG 策略变化后可升级为 `v2`。
- `semantic_id` 使用 ULID 或 UUID。
- `semantic_fingerprint` 不等于完整 query hash，而是结构化语义摘要的 hash。

### 3.3 semantic_fingerprint 结构

示例：

```json
{
  "intent": "medical_qa",
  "entities": ["高血压", "咖啡"],
  "question_type": "can_or_not",
  "negation": false,
  "risk_level": "low",
  "prompt_version": "medical_qa_v3",
  "rag_collection_version": "medical_knowledge_2026_04"
}
```

然后对该结构做稳定 JSON 序列化和哈希：

```text
semantic_fingerprint = sha256(canonical_json(payload))
```

### 3.4 语义缓存 Value

```json
{
  "answer": "高血压患者通常可以适量喝咖啡，但需要结合血压控制情况和个人耐受情况...",
  "canonical_question": "高血压患者是否可以喝咖啡？",
  "risk_level": "low",
  "model": "gpt-4o-mini",
  "prompt_version": "medical_qa_v3",
  "rag_collection_version": "medical_knowledge_2026_04",
  "created_at": "2026-05-01T10:00:00Z",
  "expires_at": "2026-05-08T10:00:00Z",
  "hit_count": 18
}
```

`canonical_question` 用于排查缓存命中是否合理，不作为 Redis key。

### 3.5 缓存命中策略

推荐命中条件：

- 向量相似度 `>= 0.95`：低风险问题可直接复用。
- 向量相似度 `0.90 - 0.95`：只允许低风险 FAQ 复用，并要求实体、意图、否定词一致。
- 向量相似度 `< 0.90`：不复用。
- `intent` 必须一致。
- 医学实体必须一致。
- 否定词和条件词必须一致。
- `risk_level` 必须是 `low`。
- `prompt_version` 必须一致。
- `rag_collection_version` 必须一致。

避免误命中的例子：

```text
高血压能喝咖啡吗？
低血压能喝咖啡吗？
```

这两个 query 向量可能接近，但医学实体不同，不能复用答案。

### 3.6 不直接复用最终答案的场景

以下问题不应直接复用缓存答案：

- 胸痛、呼吸困难、昏迷、抽搐、大出血等急症。
- 儿童、孕妇、老人用药。
- 药物剂量、用法、禁忌和相互作用。
- 检查报告异常解释。
- ECG 个体化诊断。
- 包含年龄、性别、病史、用药、检查指标的问题。
- 依赖最新指南、政策、药品说明的信息。

这些场景可以缓存路由结果、RAG 召回结果或中间判断，但最终回答建议重新生成。

### 3.7 请求流程

```text
1. 用户提交 query。
2. 规范化 query，去除多余空格、统一标点、处理口语词。
3. 提取 intent、entities、question_type、negation、risk_level。
4. 生成 query embedding。
5. 查询 Redis 向量索引 TopK。
6. 检查相似度和元数据。
7. 命中则返回 mg:semcache:answer:chat:v1:{semantic_id}。
8. 未命中则执行正常 Agent 流程。
9. 生成答案后写入语义缓存。
```

## 4. 阶段三：任务队列与 Agent 稳定性

目标：把耗时任务从 API 请求链路中拆出去，避免高并发下拖垮 FastAPI。

### 4.1 队列选型

当前阶段不建议优先引入 Kafka。推荐：

- `Celery + Redis`：实现成本低，适合后台任务、重试和定时任务。
- `Celery + RabbitMQ`：更标准的任务队列方案，可靠性更强。
- Kafka：后续用于事件流、审计日志、模型调用轨迹、跨服务数据管道。

### 4.2 队列拆分

```text
chat_queue
rag_queue
ecg_report_queue
memory_queue
embedding_queue
```

每类任务单独设置并发上限：

- 普通聊天不能被 ECG 报告生成阻塞。
- RAG 检索和 embedding 生成不能无限并发。
- LLM 调用必须有全局限流。

### 4.3 FastAPI 与 Worker 解耦

推荐模式：

```text
FastAPI 接收请求
  -> 鉴权与参数校验
  -> 查询语义缓存
  -> 命中则直接返回
  -> 未命中则创建 job
  -> 投递队列
  -> 返回 job_id
  -> Worker 消费任务
  -> 写入结果
  -> 前端通过轮询、SSE 或 WebSocket 获取结果
```

### 4.4 任务状态 Key

```text
mg:job:{job_id}
```

Value 示例：

```json
{
  "status": "running",
  "type": "chat",
  "user_id": "u_123",
  "session_id": "s_456",
  "progress": 60,
  "result_cache_key": null,
  "error": null,
  "created_at": "2026-05-01T10:00:00Z",
  "updated_at": "2026-05-01T10:00:08Z"
}
```

状态枚举：

```text
queued
running
succeeded
failed
expired
cancelled
```

### 4.5 稳定性机制

- 每个任务设置 timeout。
- 失败自动 retry。
- 超过重试次数进入 dead letter queue。
- 任务增加 `idempotency_key`，避免重复执行。
- 使用 Redis `SET key value NX EX seconds` 做去重锁。
- Worker 定期上报心跳，避免任务永久卡在 `running`。

## 5. 阶段四：LangGraph 与 LLM 调用治理

目标：避免多个 Agent 请求并发时互相影响。

### 5.1 Agent 状态隔离

- 每次请求创建独立 `AgentState`。
- 禁止共享可变全局状态。
- 全局资源仅保留无状态客户端、连接池或线程安全单例。
- 用户画像写入从本地文件迁移到数据库或任务队列。

### 5.2 超时与降级

每个关键节点应配置超时：

- Router Agent。
- Retriever Agent。
- Executor Agent。
- Web Search。
- ECG Report。
- Memory Write。

失败后应返回可用的降级结果，而不是让工作流崩溃。

### 5.3 LLM 调用限流

- 用户级限流。
- IP 级限流。
- 模型供应商级限流。
- 每个模型单独并发上限。
- 队列积压过高时返回排队状态或降级提示。

### 5.4 医疗风险路由

推荐策略：

```text
低风险 FAQ
  -> 优先语义缓存

中风险医学问答
  -> RAG + LLM

高风险症状或个体化诊断
  -> 不复用最终答案
  -> 实时生成
  -> 附带就医提醒

急症关键词
  -> 直接触发安全回复
  -> 提示及时就医或拨打急救电话
```

## 6. 阶段五：云端部署准备

目标：让服务可以多实例部署、弹性扩容、故障恢复。

### 6.1 服务拆分

推荐部署单元：

```text
frontend
api-server
worker-chat
worker-ecg
worker-memory
worker-embedding
postgres
redis
vector-db
object-storage
```

### 6.2 API 无状态化

- API 服务不保存本地状态。
- 会话状态进入 Redis 或 PostgreSQL。
- 任务状态进入 Redis/PostgreSQL。
- 用户报告、上传文件、PDF 进入对象存储。
- 多副本 API 可以挂在负载均衡后。

### 6.3 健康检查

新增接口：

```text
GET /healthz
GET /readyz
```

建议：

- `/healthz` 只检查进程是否存活，保持低成本。
- `/readyz` 检查 PostgreSQL、Redis、队列、向量库等关键依赖是否可用。
- Kubernetes 部署时配置 startup、readiness、liveness probes。

### 6.4 配置与密钥管理

- 本地开发继续使用 `.env`。
- 云端使用 Secret Manager、Kubernetes Secret 或云厂商密钥服务。
- OpenAI API Key、数据库密码、ECG 站点账号不得进入 Git、镜像和日志。
- 配置与代码分离，支持 staging、production 多环境。

### 6.5 存储迁移

- SQLite -> PostgreSQL。
- 本地 PDF -> 对象存储。
- 本地 Chroma 持久目录 -> 独立向量数据库或托管向量服务。
- 本地 profile JSON -> PostgreSQL 用户画像表。

## 7. 阶段六：可观测性与审计

目标：上线后可以定位问题、追踪成本、发现风险。

### 7.1 结构化日志

每次请求和任务执行建议记录：

```text
request_id
user_id
session_id
job_id
agent_node
latency
model
token_usage
cache_hit
queue_name
error_code
```

注意日志必须脱敏。

### 7.2 监控指标

核心指标：

- API QPS。
- API 错误率。
- P95/P99 延迟。
- 队列积压长度。
- Worker 成功率。
- Worker 失败率。
- LLM 超时率。
- LLM token 消耗。
- Redis 命中率。
- 语义缓存命中率。
- RAG 命中率。

### 7.3 审计日志

需要审计的事件：

- 登录。
- 登出。
- Token 刷新。
- 查看报告。
- 生成 ECG 报告。
- 删除聊天记录。
- 修改用户信息。
- 管理员操作。

### 7.4 告警

建议告警项：

- LLM 调用失败率过高。
- 队列积压过高。
- Redis 不可用。
- PostgreSQL 不可用。
- Worker 大量任务失败。
- 登录失败异常增多。
- 语义缓存异常命中率升高或降低。

## 8. 推荐执行顺序

```text
1. 用户系统 + 密码哈希 + JWT
2. PostgreSQL 替换 SQLite
3. Redis 接入：限流、任务状态、语义缓存
4. Celery/RQ 接入：ECG、memory、embedding 后台化
5. Chat 任务化 + SSE/WebSocket
6. Agent 超时、重试、限流、降级
7. 对象存储 + 向量库独立化
8. 监控、日志、审计、告警
9. Kubernetes / 云端多实例部署
10. 根据吞吐决定是否引入 Kafka
```

## 9. 当前阶段建议

短期优先级：

1. 不急着引入 Kafka。
2. 先完成认证安全、PostgreSQL、Redis、任务队列和限流。
3. Redis 语义缓存只对低风险、非个体化、非急症类问题启用。
4. Agent 执行链路先增加超时、降级和结构化日志。
5. 本地文件存储逐步迁移到数据库和对象存储。

这些改造完成后，系统会从“本地可运行”提升到“具备云端上线基础”的状态。
